# C18–C20 收口记录（2026-11-10）

范围：在提交 `73966ff` 及后续本地修改基础上，修复三项 GUI 生命周期缺陷，补齐 Core 校验诊断，处理本轮发现的 IPC 大响应序列化问题，并按用户反馈清理冗余说明、统一程序图标。此记录保留代码收口时的验证证据；后续提交及交付纳入 [v0.1.1-rc.4](releases/v0.1.1-rc.4.md)。

## 草稿与正常退出（C18）

草稿保存现在返回成功状态。待写入集合独立记录每个配置，即使用户已切到其他配置，失败草稿仍保留在内存并参与后续重试。只有全部待写入完成才清除保存计时器；重试成功同步清除对应保存错误和退出拦截弹窗。

托盘、程序菜单、无托盘时的窗口关闭，以及完整退出都经过草稿保存检查。完整退出先等待在途写操作，再检查草稿并发送 Shutdown；响应或原请求查询确认成功后再次检查，以保留等待期间产生的新修改。保存失败时保留界面，提供返回编辑、重试保存、导出未保存草稿和明确放弃修改的选项。Windows 导出使用文件选择器；导出的 JSON 包含配置标识、草稿基准和完整正文，失败删除项用 null 标记。其他平台提供复制副本。

“放弃未保存修改”的选择绑定当时的草稿内容；后续编辑不会沿用旧选择。已损坏的磁盘草稿仍不被隐式覆盖，必须按现有冲突处理流程明确决策。

## 设置基准与用户编辑（C19）

GetSettings 的请求代次继续隔离旧读取；SaveSettings 也使先前读取失效。用户编辑后，新的设置读取只更新后台已保存基准和首次读取完成状态，保留正在编辑的 Core、资源目录和启动选项。后续状态轮询不会再因首次响应被丢弃而自动覆盖草稿。

明确记录设置草稿是否已编辑；即使后续主动重读，仍保留未保存修改。保存正常成功和按原请求查询确认成功共用处理逻辑；保存期间产生的新修改仍受保护。

## 后台应用与草稿基准（C20）

非当前配置的应用完成后，草稿基准变化和草稿删除均加入同一待写入集合并立即持久化。保存失败保留待写入状态，继续重试并参与退出检查。正常响应与原请求查询确认共用此路径。

回归覆盖 A 的 S1 应用期间继续编辑为 S2 并切换到 B；应用完成、重开后仍保留 S2，且草稿基准等于已应用的 S1，不再误报冲突。

## 诊断与响应性

- F04：所有 Supervisor 的 Core 校验入口均接入会话诊断。失败 stdout / stderr 各最多保留 16 KiB，并按小块加入有界内存日志；持久化错误及操作结果保持通用摘要。回归确认原始诊断可通过 GetLogs 读取，但不出现在持久操作文件中。
- 即时退出补偿测试改用轻量 shell fixture，避免 Python 解释器和模块载入延迟超过 Direct 的 250 ms 观察窗口。此调整不扩展 Direct 就绪能力，F03 仍保留。
- 本轮大日志 / 慢客户端验收出现状态查询超时。响应此前在异步线程上重复序列化；现在只编码一次，移到后台阻塞任务，编码期间继续占用连接名额，取消等待不会绕过并发上限。超大响应仍在写入帧头前转换为结构化错误，保持 C11 约定。

截图反馈的冗余信息已移除，图标源、尺寸和三个接入位置见 [程序图标](ui-icon.md)。
