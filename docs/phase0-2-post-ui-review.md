## C18 / P1：草稿保存失败后仍允许正常退出

位置：[草稿保存](../crates/xray-manager-app/src/ui.rs)、[托盘退出](../crates/xray-manager-app/src/app.rs)、[窗口退出操作](../crates/xray-manager-app/src/ui/dialogs.rs)。

复现：在独立目录中用一个普通文件占据 `config/editor-drafts`，使草稿写入确定失败；编辑配置后执行托盘“仅退出界面”。实际状态同时出现保存错误和 `exit=true`，草稿未落盘。退出到达 `on_exit` 后虽然还会尝试保存，但持续写入失败不会阻止窗口关闭。窗口内的“仅退出界面”及完整退出也没有检查保存是否成功。

`stash_draft` 只记录错误，仍把草稿放入内存并清除保存计时器；调用者无法判断持久化是否成功。用户可能通过正常退出丢失尚未落盘的修改。

关闭要求：保存结果可被调用者检查；失败草稿保留待保存状态，提供重试 / 导出；正常退出失败时保留界面，只有用户明确放弃未保存修改后才继续。覆盖托盘、窗口内退出和完整退出入口，不能仅检查错误消息出现。

## C19 / P2：首次设置自动补读绕过编辑保护

位置：[设置请求上下文、状态响应及设置载入](../crates/xray-manager-app/src/app.rs)、[设置页面](../crates/xray-manager-app/src/ui/settings.rs)。

复现顺序：

1. 首次 `GetSettings` 已发送但响应尚未处理，后台已连接；用户进入设置页选择新的 Core 路径。
2. 首次响应因设置编辑版本已变化而被正确丢弃，`settings_loaded` 仍为 false。
3. 后续正常状态轮询发现设置尚未加载，自动重新发送 `GetSettings`，上下文使用此时的用户草稿。
4. 若期间不再编辑，补读响应匹配该上下文，旧保存值覆盖用户刚输入的路径。

临时探针确认：第一次迟到响应没有覆盖输入，紧随其后的自动补读却将输入改回 `stored_settings()` 中的值。登录自启 / 自动连接选项使用同一载入路径。原 C16 的配置选择导致设置读取失效场景不重新打开，此处登记为新的补读与草稿生命周期问题。

关闭要求：分别记录后台设置是否已读取和用户设置草稿是否被编辑；自动补读更新已保存基准，不覆盖用户修改。或者在完成首次设置载入前明确禁用编辑。补充“首次响应被丢弃 → 状态轮询 → 自动补读”完整回归。

## C20 / P2：非当前配置的草稿基准只更新内存

位置：[应用完成后的草稿处理](../crates/xray-manager-app/src/ui.rs) `applied_draft`。

复现顺序：对配置 A 的草稿 S1 提交应用；响应返回前继续编辑成 S2，并切到配置 B。此时 S2 以 A 的旧 Revision 保存到磁盘。S1 应用成功后，内存中 A 的草稿基准更新为 S1 的 Revision，但对应 `editor-drafts/A.json` 没有同步保存。

临时探针确认磁盘仍为旧基准；关闭并重开界面后，载入 A 的正式 S1 和草稿 S2，会误报草稿版本冲突。草稿正文仍在，未观察到此场景的内容丢失；如果本次会话先返回 A 并再次保存，可能掩盖问题。

关闭要求：更新非当前草稿基准时一并原子持久化，并按 C18 处理失败；覆盖应用正常响应和按原请求查询确认成功两条路径。重开界面后 S2 应保留且无需处理虚假冲突。

## 本轮验证与不稳定项

三个临时探针执行实际 GUI 状态处理代码并全部确认上述错误行为：

- `remaining_review_probe_gui_exit_proceeds_after_draft_write_failure`
- `remaining_review_probe_settings_retry_overwrites_initial_user_edit`
- `remaining_review_probe_background_apply_leaves_old_persisted_draft_base`

探针断言的是当前错误行为，不计为修复通过；执行后已恢复原测试文件，未向正式套件加入这些探针。本轮未操作真实系统代理、登录任务或用户 Core 进程。

默认并行的 `cargo test --workspace --locked` 首次在 `recovery_tests::failed_apply_restores_actual_running_or_stopped_state` 失败：预期启动失败，实际得到 Direct 应用成功。相同场景单独复测通过；启动实现仅等待 250 ms 后检查进程存活，时序敏感性需要继续定位。此观察归入 F03 与 V04/V09，不据一次失败推断全部补偿合同失效，也不能用随后通过抹去首次失败。

随后按 CI 使用 `cargo test --workspace --locked -- --test-threads=4`，98 项常规测试全部通过，3 项需要显式官方 Core 的专项按既有设置忽略。GUI 仍为 38 项正式测试；临时探针不计入此数字。本轮没有重跑 Windows 专项，上一轮 Windows GUI 40 项及 release 冒烟证据继续保留其原验证范围。
